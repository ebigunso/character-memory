# Plan: the retrieval result becomes the notes handed to the model, and an example carries a character through a few turns

- status: in-progress
- generated: 2026-09-23
- last_updated: 2026-09-23
- work_type: code

## Goal
- An application that has a retrieval result can hand a language model what a person would write on a card for an actor before a scene: who is here and when you last met them, what stands open between you and which way it runs, what fell due, what happened, and what you hold about the people and matters present, each memory with the scene it was recorded in. The notes come from the result alone, in one call, with no model, no clock, no store read and no judgment about what may be said; that judgment stays with the model (ADR-D-0038). A runnable example in the library shows a character writing a few experiences, meeting someone again, retrieving for the new scene, and printing those notes, deterministically and offline, so the README's worked example is real code.

## Definition of Done
- The result gains one projection, a memo: a small structured value built by a pure function from the result and rendered to text by that value's own display implementation (ADR-I-0029: structure is authoritative and prose is a projection derived by the owning type). The application may print the text or format the structure itself.
- The memo carries every admitted memory of every section of the pack exactly once, in the section reading order the Design fixes. "What happened" is one combined stream of the pack's episodes and observations, ordered by recorded time (an observation by its own time when it has one, else its episode's scene time), oldest first, cause before effect, with items that have no available time after the dated ones in pack order; the stream is built in the memo's construction as structure and not in its display. Every other section of the memo stays per section in the order the pack already has. Nothing is dropped, folded, truncated or deduplicated by the memo (ADR-D-0038, ADR-D-0018); an application that must filter does so on the structure, outside the library.
- Each entry carries the memory's own text (an episode's summary, an observation's text, a thread's title and summary, labelled in progress, an interpreted memory's text) and its standing, computed only from fields the result already reports: settled, carrying the object references of what settled it, when resolved-by is non-empty; the display says settled by and names the resolver's entry when the resolver is itself an entry of the memo, never repeating its text, and says settled otherwise; owed by you or owed to you from the direction the prospective plan reports; overdue, due today or not yet due from the due state it reports; last supported an elapsed time ago from the age of support the time plan reports; and the memory's recorded source scenes, or that a source is forgotten or missing, from the memory-scenes entry. When an actor's or counterpart's notion id equals the notion a scene reference resolved to, the memo calls that party by the words the scene gave for the reference (its name or description) and by nothing else. No score, rank, cue kind, rationale, telemetry or trace appears in the memo, since none of these is what an actor's card would say and the trace is off by default.
- The memo opens with the present as given: the scene's time, setting and each reference with its resolution, in the honest words the rulings fixed: a key or name that resolved is known and says when you last met (an elapsed time from whole seconds, or never); an ambiguous name says it could be any of several people you know; an unknown name or key says you know nobody by it; a description says it was taken as a reminder of similar surroundings and taken as nobody in particular (rulings 6, 10, 11; ADR-D-0029). The activity, if given, is echoed as found or unknown. A part not given is not mentioned; the memo never says the scene is complete.
- The elapsed phrasing is one function from whole seconds to a phrase in the largest whole unit (just now under a minute, then minutes, hours, days, years), used for last met and for the age of support, and is the only wording the library adds to a time.
- The memo addresses the character as you, never names the self's id, never adds a purpose, a name the scene or the pack did not give, an identity for a description, a disclosure verdict, a summary, or any sentence the result does not carry a typed fact for (ADR-D-0023, ADR-D-0029, ADR-D-0038, ADR-I-0013).
- A runnable example under the library's own examples writes a few experiences through the public facade on the embedded stores with scenes and fixed instants, including a commitment with a direction and a due instant, an open loop the other party later settles, and a scene the character was not in; retrieves for a new scene with the person present and no topic, then with the topic of the field guide, then with the topic of the draft; prints the memo for each; and writes the scripted reply as a new experience. It carries its own small deterministic embedding provider, reads no environment and no network, prints the same bytes on every run, and removes every store it created on exit, on panic too. What each memo contains is recorded as a baseline observation and never made an acceptance: the script is never reshaped so a memo reads well.
- The README shows the example's code and its printed memo as its worked example and describes what the memo contains, what it never does, and how to run the example.
- A retrieval selects, orders and scores exactly what it selects at the parent commit; the memo is a pure function of the result and touches no retrieval code.

## Planner-added requirements
- The memo is a structure with a display implementation, not text only. Needed because: ADR-I-0029 says tests assert variants and fields and never message text, so a text-only renderer could not be tested at all without violating the record; and an application that wants its own format would otherwise recompute the standing (elapsed time from seconds, settled from resolved-by, the direction and due phrases) and get one of them wrong, which is the one thing worth shipping here.
- The memo is a projection of the whole result, not of the pack. Needed because: the pack holds no scene references, no last interactions and no memory scenes, and those are what the present opens with and what ADR-D-0038 requires beside each memory; the phase draft's illustrative shape rendered the pack, and the draft calls that shape illustrative.
- One canonical rendering and no style value. Needed because: the draft lists the renderer's style options among planning questions and no consumer reads one; a second style enters with the consumer that needs it, and a style value with one variant is a public type with no reader.
- The standing vocabulary is a closed enum computed at memo construction from typed fields, with the display implementation as the one place its words live. Needed because: ADR-I-0029 forbids a fact carried only in prose and a message rendered in two places; the direction, due state and resolved-by fields already exist as typed facts, so the memo re-renders their meaning once and adds none.
- The memo keeps the pack's order within every section but "what happened", and prints no score. Needed because: the pack is already ranked and the score lives only in the trace; ruling 32 fixed that relevance orders the pack, and a second ranking in the memo would be one the result did not make. "What happened" is one stream of episodes and observations oldest first by recorded time, ruled from behavior: a person tells what happened as cause before effect, in one telling and not as two lists, and the time plan deferred chronological presentation to the renderer; the order is by a time the result already reports, changes membership nowhere, and is a structural order the display only walks.
- The example constructs the facade through the public constructor with settings built from explicit overrides and its own small deterministic embedding provider, about thirty lines in the example file. Needed because: the crate's test support module is compiled only for unit tests, its embedder implements a different trait from the public one, and a README example must not depend on a test feature; a consumer reading the example sees the whole program.
- Fixed instants and caller-supplied ids in the example. Needed because: the example is the README's evidence and the companion repository's reading instrument, and both need the same bytes on every run; a scene at now would change the elapsed phrases daily.

## Scope / Non-goals
- Scope: the memo module, its tests, the example, the README, this plan. No decision record: the memo is ADR-I-0029's projection rule applied to the retrieval result, and its treatment of the scene is what ADR-D-0038 leaves to the renderer.
- Non-goals: any call to a model, any clock read, any store read (a notion's name is printed only where a known-as belief about it was admitted into the pack; the memo looks nothing up). A style value or options. A token budget, a length cap or any truncation (withholding). Any ordering beyond the one chronological sort of "what happened": no most-recent-first, no sort of obligations by due instant or of beliefs by age. Omission counts and reasons, which stay in the rationale. Marking a superseded memory the caller included, since the result does not name its successor with the trace off (ruling 42's known gap, not this plan's to close). Rendering the rationale, telemetry or trace. A template engine dependency: the memo is a few dozen lines of formatting over typed fields, and a dependency earns its place only where it saves original code. A hedging or register vocabulary for observations (ADR-D-0028's register and the wording of doubt are parked for later records). A prompt wrapper, a system prompt or an instruction to the model about how to use the notes. A response or remember step driven by a model in the example: the reply is scripted. The evaluation harness's own context renderer (a development aid in the companion repository; it may adopt the memo later). The short-term store, consolidation, reflection, anything for v0.3.

## Design
- Chosen, the memo: `RetrieveOutcome::memo(&self) -> Memo`, a pure function in the API layer beside the retrieval types, and `impl Display for Memo`. Structure: `Memo { scene, activity, references, sections }`, where `references` reuses the result's scene-reference results as they are and `sections` is a fixed-order list of `MemoSection { section: ContextPackSection, entries: Vec<MemoEntry> }`, except for what happened, which the memo owns as one combined stream of the experiences and observations the pack admitted, ordered by recorded time (an observation by its own time when it has one, else its episode's scene time) oldest first, with any whose time is unavailable after them in pack order; `MemoEntry { memory: MemoryObjectRef, text: String, standing: Vec<Standing>, sources: Vec<SourceScene> }`, with `sources` reusing the result's source-scene type joined by object reference from the memory-scenes list. `Standing` is a closed enum: `Settled { by: Vec<MemoryObjectRef> }`; owed by you; owed to you; overdue; due today; not yet due; last supported, with whole seconds. The display of settled says settled by and names the resolver's entry (its section and position in the memo) when the resolver is itself an entry, never repeating its text, and says settled otherwise; it looks nothing up. A party's words: when an actor's or counterpart's notion id equals a resolved scene reference's notion, the entry carries the words the scene gave for that reference, so the display can say owed to Bob where the scene said Bob, and says owed to you or owed by you with no name otherwise. The elapsed phrase is one crate-internal function from whole seconds. Reading order of the sections: what stands between you (commitments, open loops, relationship notes, threads labelled in progress), what happened (one combined stream of the pack's episodes and observations, oldest first by recorded time, an observation's own time where it has one and its episode's scene time otherwise, ties keeping pack order, items with no available time after the dated ones in pack order, the stream built in the memo's construction as `Vec<MemoEntry>` rather than two section lists), what you hold (preferences, character signals, derived memories); an empty section is not printed and an empty memo says nothing comes to mind after the present. Evolution: v0.3's reflection may add a standing for an unconsolidated note; the display stays the one place. Verification: service-free on the embedded stores through the public facade; tests assert on `Memo` variants and fields (typed membership of every admitted memory, the stream's order, the settled references), and the one text check is scoped: within the display's body for a section, each entry's own text appears once and in the entry order, which is data and not wording; no once-only check runs across the whole memo, since a settled entry names its resolver's entry. Operation: one pass over the result, no allocation beyond the memo. Human: the text reads as a card handed to an actor. Safety: nothing is withheld, nothing is added.
- Alternative: a text-only renderer, `render(&self) -> String`, as the draft's illustrative shape. Rejected: ADR-I-0029 leaves it untestable except by message text, and an application wanting another format recomputes the standing itself.
- Alternative: a method on the pack, as the draft's snippet has it. Rejected: the pack cannot say who is here, when you last met them or where a memory was recorded.
- Alternative: a template engine. Rejected: the memo is formatting over typed fields; a dependency earns its place only where it replaces original code, and none is replaced here.
- Alternative: a style value with one default variant, reserved for later. Rejected: a public type with no reader; the draft lists style options as a planning question, and a second rendering enters with its consumer.
- Alternative: print scores or cue kinds beside entries so the model knows why a memory came. Rejected: they live only in the trace, an actor's card carries no numbers, and the pack's order already says it.
- Chosen, the example: `examples/a_few_turns.rs`, run with `cargo run --example a_few_turns`. It builds settings from explicit overrides (embedded vectors under a `tempfile::TempDir`, a dev-dependency examples can use, so the directory is removed on exit and on panic; in-memory graph and statistics; no environment read), opens the facade through the public constructor with its own deterministic embedding provider (a bag of hashed tokens, about thirty lines, implementing the public embedding trait), and plays a fixed script over four fixed instants: day one, the character meets Bob at the workshop; Bob asks for the field guide, and the character writes the episode and a commitment to bring it, owed by the character to Bob, due on day three; Bob says he will send his draft, an open loop owed to the character; day two, Bob sends the draft, written as an episode that resolves the open loop through the public link path; day two evening, an episode with Alice at the cafe that Bob was not in; day four, the character meets Bob at the workshop again. It retrieves three times: with Bob present by key, the workshop's words and no topic; with the topic of the field guide; with the topic of the draft; and prints the memo after each. Then it writes the scripted reply as day four's episode and prints the ids the write returned, but only if the baseline confirms that every id the write mints is supplied by the example or derived from what it supplied; otherwise it prints none, so the output stays the same bytes on every run. It closes the facade before the directory goes. The reading of each memo is a baseline observation recorded in the report and never an acceptance: what Bob's presence brings with no topic, whether the settled open loop arrives at all or arrives as the day-two episode that settled it (ruling 42 says the settling itself is what comes), whether the cafe episode comes and with Alice's scene recorded and Bob absent from it. The script is never reshaped so a memo reads well; a memo that reads badly is a finding for the retrieval side.
- Alternative: the example under the tests directory as an ignored test. Rejected: the draft asks for the library's own examples so that a consumer feels the write path, and `cargo run --example` is what a consumer types.
- Alternative: move the tests' deterministic embedder under the crate's test-fixtures feature and share it. Rejected: it implements a different trait from the public one, and a README example that needs a test feature is not the program a consumer would write.
- Measurement (standing rule of 2026-09-22): this plan is exempt from the recall measurement, because the memo is a pure function of the result and neither task touches retrieval; the instrument is parent equality, the same store, scene and input retrieved at the parent commit and at each task's tip, twice, in both id orders, compared as the whole result, falsified by any difference in ids, sections, order or scores. For the memo itself the falsifier is completeness: any admitted memory or any scene reference of the result absent from the memo, or present twice, or in another order than the pack's outside the "what happened" stream, or within it in another order than recorded time oldest first with undated items after the dated ones in pack order, falsifies the design; the stream is the one reorder the memo makes. The companion evaluation repository holds no rendering or narrative check today (its scenarios assert on the native result, its fixture header says stories concern what arrives in recall and never what the character chooses to say, and its own two context renderers are a development aid its value audit already marks oversized), so the example's printed memo is the reading instrument: the evals worker runs the example at Task_2's tip and files the output beside the companion's D4 (meeting a person) and D1 (what fell due) narrative scenarios as evidence for the decider's read, and any line a person would not put on an actor's card is a finding. Each item is carried as a command validation owned by the orchestrator whose detail names the evals worker as the runner.
- Why chosen: the smallest thing a consumer would otherwise write wrongly (settled from resolved-by, owed which way, due which way, seconds into words, a description as a reminder and not a person, the recorded scene beside each memory) shipped as one projection with one display, and one example that makes the README true. Fit: philosophy 9.3 (rendering help follows the distinction between what the character may say and what shapes it, gist and stance over quotation) and "the character knows how things stand before it has reflected"; the phase draft section 2.4, its acceptance criterion and section 9; ADR-D-0018, D-0020, D-0023, D-0029, D-0038, ADR-I-0013, I-0029; rulings 6, 10, 11, 20, 32, 42.
