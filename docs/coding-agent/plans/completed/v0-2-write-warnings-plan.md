# Plan: the library tells the writer when what it is about to store will not do what the writer means

- status: completed
- generated: 2026-09-22
- last_updated: 2026-09-22
- work_type: code

## Goal
- An application author who writes a memory that will silently misbehave later learns it at the moment of writing, in the same place the library already reports its one existing warning, and is never refused. Two situations this phase found: a memory that settles a matter but shares no subject and no thread with what it settles, so "we settled it" never comes on meeting the person; and a person listed twice by key in one scene, so the stored scene says they were there twice and their words are indexed twice. Each is stored exactly as given (ADR-D-0029) and reported as a warning the writer can read by kind.

## Definition of Done
- `validate_plan` and `remember` report, on the candidate concerned, a warning when a `Resolves` or `FulfillsCommitment` link's resolving memory shares no subject (entity) and no thread with the memory it resolves, and when one participant key appears more than once in a scene. Each warning is a variant of the existing `CandidateValidationIssue`, carried in the existing `warnings` list of the existing `CandidateValidation`, and its `kind` tag (the enum's existing serde tag) is the stable identifier a reader asserts on. No new public type; no new field on any public type.
- Nothing is refused, rewritten, deduplicated or reordered because of a warning: the plan commits exactly as it does today, with the scene as given, and a replayed write compares equal to the original.
- Every warning is deterministic from the plan and from the objects the validator already fetches by reference; no warning reads a clock, calls a model, scans the store, or adds a graph read beyond the by-reference read the validator already makes for link endpoints.
- No configuration: no threshold, no switch. A repeated key is repeated when it appears twice; a resolver shares nothing when the intersections of the two memories' subject lists and thread lists are both empty.
- The README, which names no warning today and whose examples check only the validation status, gains one short section: where warnings appear (`validate_plan`'s validations, `RememberOutcome.diagnostics.validations` and the projected messages), each kind with the situation it means and the behavior that follows if it is ignored, the existing echo warning included; it also says that a one-string `remember` indexes the same text as the episode summary and as the observation and therefore carries the echo warning, and how to write a distinct summary; and it says that recency and last met see an experience only at reference times at or after its scene time.
- Every kept case is shown at the parent commit first: the write passes with no warning there, and a retrieval shows the consequence (the settled matter absent from where things stand on meeting the person; the person reported twice).

## Planner-added requirements
- The warning kind is the variant's existing serde tag and nothing more. Needed because: `CandidateValidationIssue` is already tagged `kind` in snake case and its `Display` text is already projected into `RememberDiagnostic` messages under the code `WritePlanValidationWarning`; the companion evaluation repository reads only `CandidateValidationStatus` today and asserts on no warning, so a second identifier scheme would have no reader.
- A warning attaches to the candidate that carries the mistake: the link candidate for a resolver, the episode candidate for a repeated key. Needed because: `CandidateValidation` is per candidate and a reader finds a warning by `candidate_index` and `candidate_kind`, as the echo warning is found today.
- The resolver check uses what the validator already fetches. Needed because: `PlanValidationContext` already queries every link endpoint not in the plan by reference to prove it exists; keeping the fetched interpreted memories' subject and thread lists beside their references costs no read. A resolver or target in the plan is read from the plan's own candidate. If an endpoint is neither in the plan nor in the graph the existing unknown-reference error already fires and no warning is added.
- The library never judges the time the application perceived. Needed because: decision 3 says the time is never guessed and ADR-D-0029 says the scene is given as perceived; a scene time later than the record's creation is only invisible to recency and last met until the retrieval reference time reaches it, which is a property of the reader, stated in the README, not a mistake in the write.

## Scope / Non-goals
- Scope: the production modules, test files and documents the task lists under owns, this plan.
- Non-goals: the near-verbatim superseding restatement and chain-churn warnings the phase draft names (each needs a heuristic and a threshold nobody has measured; they wait for the generation phase whose restatements they judge). A warning on a scene time in the future of the record's creation (dropped, see Design). A warning for an interpreted memory given by the application with no experience behind it (dropped, see Design). A warning for a description that matches earlier words in the store, or for a blank participant (dropped, see Design). A warning on the `link` facade method (see Open Questions). Any refusal. Any rewriting of the scene, the participant list or the subject lists (decision 2 already treats the entity and thread id lists as sets; the scene is stored as given). Warnings during retrieval. A warning severity or category beyond the existing error/warning split.

## Design
- Chosen, the shape: two variants on the existing `CandidateValidationIssue`, produced inside `PlanValidationContext::validate_candidate` next to the echo warning, pushed onto the existing `warnings` list, and reaching the caller through the two readers that exist: `validate_plan` (the validations) and `remember` (the validations with warnings kept in `RememberOutcome.diagnostics`, plus the projected messages). Structure: the context keeps, for each fetched interpreted memory, its subject and thread lists alongside its reference (today it keeps only the reference); the resolver check runs on a link candidate whose relation is `Resolves` or `FulfillsCommitment` and whose two endpoints are interpreted memories, reading each endpoint from the plan or from the fetched objects. The repeated-key check runs on the episode candidate from the draft alone. Evolution: a later warning is one more variant in the same place. Verification: each warning is shown absent at the parent commit and present after, through `validate_plan` on the real embedded stores and through `remember`'s diagnostics; the commit is shown unchanged with and without the warning. Operation: no new read, no clock, no model; the write turn's cost is unchanged. Human: the application author reads the `kind` and the README line for it. Safety: warn-only; nothing is stored differently.
- Measurement exemption (decider's standing rule of 2026-09-22): this plan changes nothing that comes to mind, its order or its standing, because warnings are advisory at write time and recall is unchanged, so no measurement validation is required; the acceptance's trace-off equality of retrieval with and without the warning is the check, and the companion driver's warning-status drift test is the evidence.
- Alternative: a stable code enumeration beside the variants (a `code()` accessor or a separate `WarningKind` type). Rejected: the serde tag is already that code and the companion asserts on none; a second scheme is a public type with no reader.
- Alternative: warnings produced at `prepare`. Rejected: `prepare` has no graph, so the resolver check cannot run there, and the repeated-key check would then live in a second place; one place, the validator, serves both `validate_plan` and `remember`.
- Chosen, the kept candidates and why: (a) the resolver sharing nothing with its target: reader the application author, consequence stated in decision 42 (the matter leaves where things stand and the settling never comes on meeting the person). (e) a key repeated in one scene: consequence that the stored scene names the person twice, recall reports them twice, and their words are joined twice into the participants surface (decision 13 drops blank entries only; ADR-D-0029 keeps everything else as given, so the repeat is stored).
- Dropped candidates and why: (d) a scene time after the record's creation: the only instant the write path holds is `created_at`, the process clock at prepare, while visibility to recency and last met depends on the retrieval reference time, which the write cannot know; a device stamping a few seconds ahead would warn on every write; and decision 3 says the library never judges what the application perceived. The README states the reader's rule instead. (b) an interpreted memory given by the application with no experience behind it: `given_by_application` is an explicit declaration, its consequence (no scope key, so no setting or custom value brings it, while its subjects and its topic still do) is the honest meaning of having no experience, and the warning would fire on every seeded memory; the README states the consequence instead. (c) a blank or whitespace participant: already dropped silently under decision 13, the writer meant nothing by it and nothing is stored, so there is no behavior to warn about; a description whose words were given with a key before in this store: needs a search over stored words or a store scan, which the cost rule forbids, and ADR-D-0029 says a description is never an identity, so matching words prove nothing. (e) narrowed: two keyless participants with identical words are not a repeat (two people can look alike; a description is never an identity), so only a repeated key warns. (f) the existing echo warning is not misled by the scene-words change: it compares the observation or derived text with the episode summary, and scene words live on their own surfaces, so the compared texts are unchanged; it does fire on every one-string `remember` because the helper copies the content into both the summary and the observation, which is accurate about what gets indexed twice, so the README says so and how to avoid it, and nothing in the machinery changes.
- Why chosen: the smallest form that gives each situation this phase found a warning with a reader and a stated consequence, in the machinery that exists, with no number and no read added. Fit: the phase draft section 2.3 ("the write path warns, never blocks"); ADR-D-0028 ("quality is enforced at the write path and never by manipulating memory afterward"); ADR-D-0029 (stored as given); decisions 2, 3, 13, 36 and 42.

## Notes
- Risks: an application that already writes resolutions with no shared subject by design (a resolver about a thread only, say) gets a warning on each; the warning is accurate (the state route brings current memories by subject) and the thread intersection quiets it when the thread is shared. A test fixture that repeats a key gains a warning and no other change.
- Edge cases, with the expected result: a resolver that is also the target (a self link) is already an error and warns nothing more; a resolver whose only shared subject is the character itself counts as shared; an episode with no participants warns nothing; a link between an interpreted memory and an episode by `Resolves` is outside the rule and warns nothing; a scene time in the future is stored as given and warns nothing.
