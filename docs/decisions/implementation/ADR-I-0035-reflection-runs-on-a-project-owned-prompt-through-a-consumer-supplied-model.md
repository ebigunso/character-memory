# ADR-I-0035: Reflection runs on a default prompt the project owns, through a completion port the consumer implements, and the library hard-codes no model

## Context and Problem Statement

Consolidation needs a language model. A port alone means nobody can reflect without authoring a quality-critical prompt as well as integrating a model, and then trace accumulates indefinitely and the character never forms lasting memory from it, which defeats the design. A bundled model client means the library tracks vendors and versions forever and excludes anyone running a model it does not support. The fork is what the library ships and what the consumer supplies.

## Decision

The library ships a default reflection prompt that the project owns, versions, and evaluates, and the consumer may override it. The consumer supplies the model by implementing a minimal completion port, in the pattern of the embedding provider. The library carries no model client and names no model.

The library asks the model for structured output and validates it through prepare, validate, and commit, including the evidence rules of ADR-D-0028, so output that is malformed, ungrounded, or structurally unsupported yields diagnostics and an unreleased trace. This is structural validation, not semantic safety: a schema-valid misjudgment can still commit, which is why evaluation measures them and a later reflection can supersede them. Which prompt ran is reported on the reflection's outcome and in the log, as the project's prompt version or, for an overriding prompt, a digest the library computes from its text, so an override is identified without the consumer keeping a versioning scheme, and is not stored on the memories a reflection produces: supersession never reads it, consumed trace is gone so nothing can be re-reflected by version, the evaluation harness pins the prompt in its own manifest, and a prompt identifier without the model that ran it, which the library never knows, identifies little. Content excluded when it is written never reaches the prompt because it was never stored: exclusion is applied at the mechanical write (ADR-D-0026), and the prompt builder checks again as a second guard. Content excluded afterward is kept out of every prompt built from then on; what a reflection already in flight had sent cannot be unsent, and the boundaries for that case are stated below. Reflection's input is bounded, and a long span is processed in order in bounded pieces. Short-term entries are released only after the plan that consumed them commits, and the release is idempotent. Consolidation is one recoverable operation over a record the short-term store keeps: a reflection first claims the entries it selects, atomically, so no two reflections hold the same entry; it records the validated plan against that claim before it commits; the plan's identifiers are derived from the entries it consolidates, so committing it again writes nothing new; and a claim ends in one of two ways: with the release, after its plan committed, or with an abort, which frees the entries and keeps their trace. Malformed output, a validation failure, and a commit rejected because an entry was excluded or a superseded memory was no longer current each abort the claim, discarding any plan recorded against it, so a later reflection selects those entries afresh. The rule is general and those are only its commonest cases: every way a reflection can end before its claim is marked committing, an error or timeout from the completion port, the application cancelling or dropping the call, any failure at all, aborts the claim as it ends, so no finished or cancelled reflection holds an entry while the process stays open. A failure after the mark, an I/O error partway through the writes, is retried in the same process by replaying the recorded plan, and is left to recovery at the next open only if the process ends first. A crash between commit and release is therefore finished on the next open by replaying the same recorded plan and releasing, never by composing a different plan over the same trace, and recovery reads the claim's state, never the durable stores, because a commit is not one write: objects and links are persisted in separate steps and a crash can leave some of them behind. At its serialized turn, after its checks have passed and before its first durable write, a commit marks the claim as committing. Recovery finishes a committing claim by replaying its recorded plan to the end, which completes whatever was partly written, since the identifiers are derived and every write is an upsert, and then releases; it aborts a claim that never reached committing, since nothing durable came of it.

Scheduling is the application's: the library reports what has accumulated since the last reflection, and why, for the stretch a write or a recall belongs to and for the store as a whole, and also under a key where the application gave one; accumulation is counted over stretches because a stretch exists at the mechanical write and a scope is known only once consolidation has resolved it, and it selects a reflection's bounded input by stretch; it never runs reflection on its own. Reflection is safe to run beside recall, mechanical writes, and exclusions on the same memory. Recall is a reader of the same serialization: it never runs inside a mutation's turn, and a reflection's turn holds its writes and the release of its trace together, so a recall sees memory as it stood before a commit or as it stands after, never objects without their links and never a durable memory beside the trace it was made from. The model call happens outside any turn, so recall waits only on local writes and never on a model, and recovery of a committing claim finishes before the first recall after an open. Every operation that changes durable memory takes one serialized turn within the process that owns the stores, which is the only writer the embedded stores admit: a reflection's commit, a caller's commit, a correction, a forgetting, a direct link, and an exclusion alike. A recheck is only as good as what it is serialized against, and a correction slipping between a reflection's check and its write would fork a chain as surely as a second reflection. At its turn a reflection's commit checks again that the durable memories it read and supersedes are still current and rejects the plan otherwise, so two reflections cannot fork one supersession chain. The claim records which entries were selected and the version of each, and commit checks them again: if any selected entry has since been excluded or otherwise changed, the plan is rejected, nothing commits, nothing is released, and a later reflection selects afresh. An exclusion takes the same serialization as a commit, so the two never interleave: an exclusion that comes first changes the version and the commit at its turn is rejected, and no exclusion can land between a commit's check and its write. An exclusion therefore wins over a reflection exactly until that reflection's claim is marked committing, which is the boundary a caller can rely on. One that arrives after the commit finds the entry already consolidated, and its outcome says so and names the memories the recorded plan derived from that entry, so the application can suppress or purge them, which is what ADR-D-0026 prescribes once something has been consolidated. What it cannot do is retract text already sent to the model before the exclusion was issued; the guarantee is that excluded text is never sent after it is excluded, and never produces memory when the exclusion comes before the claim is marked committing.

## Why

Owning the prompt keeps the quality-critical instructions with the project that can evaluate them, while taking the model through a port keeps the library free of a maintenance surface that changes monthly and open to any model a consumer can call. ADR-I-0013 is unchanged: deterministic helpers still infer nothing, and inference lives behind this port.

## Rejected Alternatives

- A port with no default prompt: rejected because every consumer would have to author and evaluate a quality-critical prompt before trace could ever be consolidated; the default removes prompt authoring, while integrating a model stays the consumer's by design.
- A bundled client for named models: rejected because of the maintenance surface and because it excludes unsupported models; reopen only as an optional companion crate outside the library.
- Free-text reflection output parsed heuristically: rejected outright; the write path validates structure.
- The prompt version recorded on every memory a reflection produces: rejected because nothing reads it, as above, it costs a field on every interpreted memory, and it obliges every consumer who overrides the prompt to keep a versioning scheme; an application that wants the history keeps the outcome it was handed. Reopen as one record per reflection run if a need to find a run's outputs appears. The catalog's F19, that the record shows which reflection concluded what, is met without it: the earlier conclusion stays in the record, superseded, beside the one that replaced it, each with its time and the evidence it rested on, and a reflection is told from another by when it concluded.
- A scheduler inside the library, including an opt-in background worker that triggers on scene boundaries and accumulation: rejected because what counts as a finished conversation or a finished action log differs widely between applications, and only the application knows it and what a call costs; any default timing would be an arbitrary assumption that constrains how the library can be used. Reflection needs no idle character, so the application is free to start it in the background whenever it judges an event finished; the library provides the signal, the selection, and safe concurrent execution.

## Decision Boundary

Invariant: the project owns a versioned default prompt that consumers may override; the model arrives only through the consumer's port; output is structured and validated; which prompt ran is reported on the outcome and never stored per memory; an entry is claimed by at most one reflection, and a claim ends only by release after commit or by an abort that keeps the trace; the plan is recorded before commit, the claim is marked committing before the first durable write, and a committing claim is replayed to completion, not recomposed or abandoned, after a crash; every operation that changes durable memory, and every exclusion, takes one serialized turn, and a reflection's commit rechecks what it supersedes at its turn; every exit before the committing mark aborts the claim, and every failure after it is replayed; recall never observes a turn in progress; trace is released only after commit; the library schedules nothing.

Not covered: the form of the claim record and of the commit serialization, including the conditional upsert the write path itself still lacks; the port's exact signature, the output schema, the prompt text, the signal's thresholds, the piece size, and the guide's recommended schedules.

## Validation

- Reflection runs end to end with a test double implementing the completion port and no network.
- Malformed or rule-breaking model output produces diagnostics, commits nothing, and releases nothing.
- A reflection's outcome names the prompt that ran, the project's version or the digest of the overriding prompt's text, two different overrides report different digests, and no stored memory carries either.
- A reflection running beside concurrent recall and writes on the same scope leaves a consistent supersession chain.
- A commit paused between writing its objects and its links is invisible to a concurrent recall, which returns either the state before the commit or the state after it, and never both a consolidated memory and the trace it came from.
- Two reflections started together over overlapping trace never consolidate the same entry twice: one claims it and the other does not see it.
- A completion port that errors or times out, and a reflection the application cancels, each free the claimed entries at once, in the running process, with their trace intact.
- An I/O error after the committing mark is replayed to completion in the same process.
- A correction issued against a memory while a reflection that read it is committing waits its turn or goes first, and in either order the supersession chain has one head.
- Malformed output, a validation failure, and a rejected commit each free the claimed entries with their trace intact, and the next reflection selects them again.
- A process killed after a plan was recorded and before the claim was marked committing, on reopening, aborts the claim and writes nothing.
- A process killed partway through a commit, with some objects written and no links, on reopening, replays the recorded plan to completion, leaves no partial memory and no duplicate, and releases the trace.
- A process killed after commit and before release, on reopening, replays the recorded plan, writes no duplicate, and releases the trace.
- Two reflections that would supersede the same durable memory commit one after the other, and the second is rejected and retried against the new state.
- An exclusion issued while a commit is in progress waits for it, and then reports the entry as already consolidated together with the memories derived from it; it never lands between the commit's check and its write.
- An entry excluded after a reflection selected it and before that reflection's claim is marked committing causes the commit to be rejected: nothing derived from it is written, nothing is released, and the next reflection does not see its content; the test records that the first reflection's model call had already received the text, which the design does not claim to prevent.

## Revisit When

Structured output proves unattainable on the models consumers actually run, or the default prompt cannot be evaluated without pinning a model family.
